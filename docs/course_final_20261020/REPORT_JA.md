# 限られた計算資源でのVLA適応と閉ループ動作の検証

## 動作実行周期とチャンク境界平滑化を中心とした実践報告

Physical AI 応用編1 最終課題・技術報告案\
作成日：2026年10月20日

### 要旨

本課題では、画像・言語・ロボット状態から動作を予測するVision-Language-Action（VLA）モデルを、限られたGPU資源で適応・配備し、閉ループ実行で何を検証すべきかを調べた。Axis Pi0.5を基盤に、動作expertのLoRAと入出力・時刻処理層を更新したR6モデルを用いた。学習対象は全パラメータの約0.72%に限定し、40タスク・1,693エピソードで500回の最適化更新を行った既存実験を整理した。さらに、予測チャンクの実行長と境界平滑化を評価した。最終比較では公開LIBERO90の15組の完了試行に対し、平滑化によって手先RMS jerkの平均は11.7567から9.9146へ低下した一方、目標達成は2件のまま、非対象物体の変位に関する代理失敗は12件から13件に増えた。この結果から候補の採用を見送った。成果は得点改善の主張ではなく、モデル・正規化・実行器の同一性を保ち、成功、滑らかさ、物体への影響を分けて判断する検証手順と、その否定結果である。

## 1. 背景と目的

VLAを動かすには、事前学習済みモデルの選択に加え、観測の整形、状態と動作の正規化、推論待ち時間、動作を環境へ返す周期を揃える必要がある。π0.5は画像・言語とロボット動作を扱う基盤モデルの一例である[1]。本課題ではその系統のAxis公開重みを利用した。基盤モデルの構築そのものは本課題の成果に含めない。

取り組んだ問いは二つである。第一に、全重みの再学習が難しい資源条件で、小さな更新範囲を使って動作適応の経路を構成できるか。第二に、同じ重みでも、予測した動作を何ステップ実行してから観測し直すか、またチャンク境界を平滑化するかで、閉ループの結果がどう変わるかである。後者について、動作列の数値が滑らかになることと、タスク達成や周辺物体の保全が改善することを区別した。

## 2. 方法と自分の担当範囲

### 2.1 システムの流れ

処理は「主カメラ・手首カメラ・指示文・ロボット状態 → 前処理と正規化 → VLA推論 → 反正規化と動作後処理 → 動作キュー → シミュレータ → 次の観測」の順である。学習にはOpenPI系の実装[2]を利用し、配備時には変換した推論重みと対応するprocessor資産を組み合わせた。

予測長をH=10とし、そのうち先頭kステップを実行してから再推論する。ここでkはexecute長であり、Hとは別の設定である。kを短くすると観測に戻る機会が増えるが、推論回数も増える。したがって、execute4がexecute8より常に優れるとは仮定しない。学習データの10 Hzと過去の配備条件である20 Hzの違いも残るため、単にステップ数だけを合わせて時間的整合性を主張しない。

### 2.2 プロジェクトで実装・検証した部分

独自の作業は、LoRAの更新範囲と数値安定性の切り分け、観測・動作変換と推論サーバの接続、実行長の切替、境界平滑化、固定初態での対比較、失敗を含む記録と候補採否の判断である。LoRA[3]、基盤モデル、LIBERO環境[4]自体の発明を主張するものではない。

R6ではaction expertのattention/FFNへrank 32のLoRAを加え、action入出力projectionとtime MLPも更新した。PaliGemma、vision、および基盤部分を凍結し、更新対象を18 leaves・24,284,192パラメータ、全体の0.7194%とした。小規模な更新範囲は計算資源上の選択であり、その選択だけで汎化が保証されるわけではない。[E1]

最終段階ではモデル読込み前の入力検証と完全な実入力によるwarmupを整備し、実際の読込み・warmup・HTTP推論を確認した。これらの配備修正の採用と、動作平滑化候補の採用は別々に判断した。RTC（Real-Time Chunking）は本課題の検証済み機能に含めない。[E4]

## 3. データと学習

### 3.1 R6の学習条件

| 項目 | 記録から確認できる条件 |
| --- | --- |
| 初期重み | 公開Axis Pi0.5 dense重み、zero-delta LoRAから開始 |
| データ | physical-intelligence/libero、40タスク、1,693エピソード、273,465フレーム |
| 時間・予測対象 | native 10 Hz、再標本化なし、horizon 10、有効7次元動作のみの損失 |
| 正規化 | fresh QUANTILES。配備時は実際のprocessor資産との対応も照合 |
| 最適化 | FP32 AdamW、最大学習率1e-6、warmup 100、勾配clip 0.1、EMAなし |
| バッチ・更新 | 2 GPU、各microbatch 1、勾配蓄積32、有効global batch 64、500更新 |
| 保存時点 | 0 / 1 / 10 / 25 / 50 / 100 / 250 / 500更新 |

R6は四つの更新範囲を比較した短いスクリーニングの後、選んだ構成を公開初期重みから500更新で学習し直した。短い試行のcheckpointをそのまま継続したものではない。FP32を用いたのは既存実験の資源・数値安定性条件に合わせたものであり、他の精度や構成より普遍的に優れるという比較結果ではない。[E1]

### 3.2 後続データ整備との区別

後続のR2では、公式native36の1,800記録・311,370フレームについて前処理とbatch入力の検査を完了した。タスクfamily単位で31/5に分離し、学習側1,550・検証側250とした。ただし、人手の記録とnative項目の厳密な対応、および新しい正規化資産を使った学習checkpointから推論までの閉路は未完了である。この1,800記録をR6の実学習件数に加えたり、入力検査の完了を新モデル学習の完了と読み替えたりしない。[E2]

## 4. 実験設計

### 4.1 過去のR6比較と実行長

既存の固定seed・80例のローカル対比較では、Axis初期重み48/80に対しR6 step500は49/80、勝ち/負け/同点は9/8/63だった。成功率差のbootstrap 95%区間は約−0.0875から0.1125で、ゼロをまたぐ。したがって、この比較だけでLoRAによる確実な改善とはいえない。[E1]

後続のexecute長比較でも改善は一貫しなかった。native R6のexecute4は二巡で6/8、7/8、execute8対照は7/8、7/8だった。新たに成功した例はなく、成功の喪失と非対象物体変位の代理失敗が各1件あり、二つの平均jerkも悪化した。これは短い実行長を標準にする根拠にはならなかった。[E2]

### 4.2 最終の境界平滑化比較

公開LIBERO90から8タスクを固定し、各2初態、各エピソード最大500 policyステップとした。タスクの正確な指示名は実際のR6の40タスクmanifestと重複しないが、操作familyには重複があり、Axis事前学習への露出も不明である。そのため「未知技能」や「完全な未見データ」の評価とは呼ばず、公開タスクによるローカル転移代理と位置づけた。[E3]

候補はexecute8を維持し、新しいチャンクの最初の動作だけを変更した。反正規化・後処理後のarm 6次元について、返す動作を「0.9 × 現在の動作 + 0.1 × 直前に返した動作」とした。gripperは変更しない。全時刻にEMAをかける方法ではない。候補は一つに限定し、確認群の結果を開く前に係数とソースを固定した。[E3,E4]

16組のうち診断群8組・確認群8組を予定したが、候補1回が記録処理の一時ファイル競合で中断した。287 policy行と10 settle行を残し、その例はモデル成功にも失敗にも数えず、再実行せずに除外した。最終解析は診断8組・確認7組、計15組である。[E3]

### 4.3 評価指標と比較可能性

主に、目標達成件数、非対象物体の最大L1変位が0.001 mを超えた件数、手先と関節のRMS jerk、成功までのpolicyステップ数を確認した。変位は周辺への影響を見る代理指標であり、公式の衝突率ではない。jerkは保存したシミュレータ軌跡に対する既存scorer値であり、返却コマンドの差分とは区別した。数値の解釈は同じscorer・時間設定の範囲に限定する。

15組とも初期シミュレータ状態と非画像入力は逐値一致した。画像を含む6入力すべてが一致したのは13組であり、残る2組では各196,608要素中3要素に1階調差があった。全入力が完全一致したとは主張しない。また、初態の復元とエピソード全体のexact replayは別であり、後者は未評価である。保存した生の7指標、計217値の再計算では最大誤差0を確認した。[E3,E4]

## 5. 結果

### 5.1 最終15組の対比較

| 指標 | 基線 | 境界平滑化候補 |
| --- | ---: | ---: |
| 診断群の目標達成 | 2 / 8 | 2 / 8 |
| 確認群の目標達成 | 0 / 7 | 0 / 7 |
| 全体の目標達成 | 2 / 15 | 2 / 15 |
| 非対象物体変位の代理失敗 | 12 / 15 | 13 / 15 |
| 目標達成かつ変位代理を通過 | 0 / 15 | 0 / 15 |
| 手先RMS jerkのエピソード平均 | 11.7567 | 9.9146 |
| 成功した2エピソードの合計policyステップ | 535 | 591 |

手先RMS jerkは15組中10組で低下、5組で上昇し、組ごとの相対変化の中央値は−6.62%だった。平均値には改善がある一方、case10では9.6780から28.3514、case14では10.0491から23.6011へ上昇した。成功した2エピソードも277→322、258→269ステップと長くなった。成功エピソードのjerk平均は軌跡長の違いの影響を受けるため、それだけで同じ仕事を効率よく実行したとはいえない。[E3]

確認群case03では、初回入力の6項目がすべて一致しているにもかかわらず、非対象物体の最大L1変位が0.000692513 mから0.026785357 mへ増え、閾値を超えた。微小な画像差があった2組を除外しても、この回帰は残る。目標達成の増加がなく、物体への影響も悪化したため、候補は既定の動作へ昇格させなかった。配備修正のみを保持した。[E3,E4]

### 5.2 歴史的な競技記録の扱い

| 歴史的設定 | ユーザー記録の結果 | 今回の解釈 |
| --- | --- | --- |
| R6 FAST、chunk10 / execute8 | T1 0.47、T2 0.33 | 過去の原ZIP 95415a…に紐づく記録 |
| R6 FAST、chunk10 / execute4、9月16日 | T1 0.364、T2 0.3457 | 過去の原ZIP 2f2f9c…に紐づく記録 |

以上は保存された過去のユーザー報告であり、公式提出IDや画面の照合は本課題では行っていない。T2の0.3457はexecute4の記録であり、今回の境界平滑化の成果ではない。現在の再構築サーバも当時の原提出ZIPそのものではない。10月のR2には新しい公式得点がなく、2/15というローカル結果を競技得点へ換算しない。[E5]

### 5.3 計算資源と終了条件

10月20日の最終比較は、4回の初期化、32回のエピソード試行（31完了・1中断）、15組の完了対比較で終了した。GPU占有の累積wall時間は4,738.987秒、2台を全時間占有した保守的計算で2.633 device-hoursだった。この段階のoptimizer更新は0であり、過去のR6学習全体の費用を表す数字ではない。完了エピソードのpolicyステップは14,626、中断分の保存済み287行を含む記録下限は14,913で、終了瞬間の厳密な実行総数は不明である。全体を追加学習せずに閉じ、失敗した記録も残した。[E4]

## 6. 考察と限界

第一に、平滑さはタスク品質の一部分だった。境界の操作でjerk平均が下がっても、目標達成、非対象物体への影響、所要ステップは同時には改善しなかった。これは「平滑化は常に無効」という証明ではなく、今回の係数・実行長・モデル・小規模な評価セットでは採用根拠が得られなかったという結果である。事後に有利なエピソードだけを選ばず、確認群と悪化例も含めて判断したことが本課題の主要な学びである。

第二に、学習と配備の間には、重み以外の同一性が必要だった。同じR6という呼称でも、native JAX版、変換後のFAST版、異なるnormalizer、execute設定の違いがある。本プロジェクトのFASTは配備用変換重みの呼称であり、FAST action tokenizerを意味しない。現在のサービスが起動したことだけで過去の得点を再現したことにはならない。

第三に、資源制限では試行の幅より、閉路が成立しているかを先に確かめる必要があった。dense full fine-tuningではメモリ問題があり、更新範囲を絞った。しかし小さなLoRAでも、データ由来、損失の有限性、保存・復元、正規化、実際の動作まで確認しなければ結果を解釈できない。後続の復元診断や新データでの正式学習は未完了であり、入力検査やログ整備だけでこの欠落を埋めることはできなかった。[E1,E2]

制約として、最終比較は8タスク・最大2初態の小標本であり、事前学習露出が不明である。微小画像差、軌跡長の差、代理変位閾値、シミュレータ限定という条件もある。実機性能、公式新タスクへの汎化、公式衝突率、RTCの効果、干渉のない完全再生は未評価である。T3の過去の0は当該評価条件で成功を確認できなかった記録として扱い、手法全体や他の取り組みの不可能性へ一般化しない。

## 7. 再現性と成果物

本報告に対応する成果は、日本語本文、要件確認表、公開用の証拠索引、元データへの内部対応表である。内部対応表には元保存先が含まれるため提出物から分離した。外部の基盤重み・tokenizer・データ・シミュレータ資産を要するため、本文とコードの取得だけで全実験を再現できる状態にはない。clean環境での完全な導入と元ZIPの再現も未検証である。

結果を追う場合は、まずモデルと正規化の識別子、タスク一覧・初態・seed、実行長・平滑化式を固定する。次に各エピソードのRESULTと保存軌跡から、成功件数、変位、jerkを同じscorerで集計し、中断例を分母から明示的に除く。生の動作・状態・接触・遅延・動画を保持すれば、集計値だけでは分からない失敗を調べられる。今回はこの方針で採否を決め、追加のパラメータ探索は行わなかった。

## 8. 結論

限られた資源の下で、基盤VLAへの小規模適応と配備・評価の接続を実践した。R6の過去の改善幅は小さく、後続の実行長短縮や境界平滑化でも信頼できる成功増加は得られなかった。一方で、動作の数値的な平滑さと閉ループの有用性が一致しない事例を、比較条件と失敗を残して示せた。今後の学習では、一つのepisodeについて観測、正規化、予測、動作、終了判定を自分で説明・再計算できる小さな閉路から始めることが有効だと考える。
